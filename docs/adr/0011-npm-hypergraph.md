# ADR 0011: The dependency hypergraph for npm

- **Status:** Accepted
- **Date:** 2026-11-03

## Context

ADR 0009 defined the hypergraph for NuGet: one node per resolved package, one hyperedge per package version that requires something, one project hyperedge, every requirement checked against the resolved version. ADR 0010 added npm ingest and kept `deprisk graph` NuGet-only, because npm differs in two ways that change what a correct graph is: a package can be installed several times (so "the resolved version of `ms`" is not one thing), and requirements are node-semver ranges.

## Decision

**Nodes are installed instances.** For npm a node is identified by its lock path (`node_modules/a/node_modules/ms`); `HypergraphNode.Path` carries it (null for NuGet). The node list is sorted by id, version, path.

**Requirements are resolved the way Node resolves them.** A package at path `P` that requires `n` gets the first installed package found by looking at `<dir>/node_modules/n` for `dir = P`, then each parent directory (directories named `node_modules` are skipped), up to the project root. The instance found is recorded as `Requirement.ResolvedPath`. If nothing is found, the requirement is *undecided* with no resolved version. Workspace links are not installed packages, so a requirement on a workspace member is undecided too (a known gap, below).

**Hyperedges.** The project hyperedge (`project:<name>`) lists every direct package under the name it was installed as (the alias for an alias install), checked against the constraint the project wrote, including packages that only a workspace member asks for. A package hyperedge belongs to one installed instance: its id is the instance's path (unique within a target), its owner is `id@version`, and `Hyperedge.Path` carries the path. Shared requirements are counted per resolved instance, not per name.

**Ranges.** `NpmVersionRange` implements the node-semver 7 grammar that appears in lock files: exact versions, comparators, caret, tilde, x-ranges and partial versions, hyphen ranges, `||`, an optional `v`, and `npm:name@range` aliases (the range after the last `@`). Prerelease handling follows node-semver (a prerelease satisfies a range only through a comparator on the same `major.minor.patch`; generated upper bounds are `<X.0.0-0`). Everything else (dist-tags, URLs, git and file specifiers, `workspace:`, malformed text, `npm:name` without a range) is not understood and makes the requirement undecided, never satisfied. The implementation is tested against node-semver 7.6.3: 106 ranges times 39 versions, expectations generated by `semver.satisfies`.

**Schema.** `graph.v1` stays version 1: `ecosystem` gains `npm`, and `node.path`, `hyperedge.path`, `requirement.resolvedPath` are added (null for NuGet). The change is additive.

## Known limits

- Dependencies between workspace members, and requirements on `link: true` packages, are undecided (first-party code is not a node).
- `includePrerelease` and loose parsing are not modeled. `x.2.3` (a wildcard followed by numbers, which node-semver reads as `*`) is rejected as not understood, which is the safe direction.
- Requirement resolution uses the lock file's tree. It does not model package-manager behaviors outside the lock (Yarn PnP, pnpm's virtual store); those have their own lock files and are out of scope.
- The hypergraph describes what is installed. Candidate versions and allowed tuples for the optimizer are still a later slice (README roadmap).

## Consequences

- `deprisk graph` works for npm; `--ecosystem` selects as for the other commands.
- A violated npm requirement is a real finding about the lock file (npm usually warns about it as ERESOLVE or an invalid peer); an undecided one is listed, never hidden.
- The optimizer (v0.3) can work on npm graphs with the same structures as on NuGet.
